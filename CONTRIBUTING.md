# Contributor Guide

We welcome anyone to contribute to `SimpleDirectedHypeanyone`, provided you adhere to the guidelines outlined below. Please read this file in full before getting to work on your first contribution.

In general, we expect that all contributors will adhere to the [Julia community standards](https://julialang.org/community/standards/#julia_community_-_standards). In particular, we expect that you will be respectful, be inclusive, and give others credit for their contributions.

## Bug reports

If you notice a problem with `SimpleDirectedHypergraphs.jl`, please file a bug report. This could include code that crashes, that produces incorrect outputs, or that is excessively slow.

Though we mirror to GitHub to facilitate integration with the Julia registry, development on `SimpleDirectedHypergraphs.jl` happens on Codeberg. Accordingly, please submit your report as a [Codeberg Issue](https://codeberg.org/CoReACTER/SimpleDirectedHypergraphs.jl/issues), including a minimal working example (including any necessary data) that demonstrates the problem that you're reporting. If the problem involves incorrect outputs, please also include the correct result (with comparison to the incorrect output result) in your report.

Please always include version numbers of all relevant libraries and Julia itself.

## Development guidelines

### "AI" Policy

`SimpleDirectedHypergraphs.jl` does not accept any code submissions generated by large language models or related "AI" tools. If you have used any "AI" to generate, edit, format, document, or test your code, please do not under any circumstances submit that code in a PR.

### Correctness

Any code that you submit must be correct. To ensure correctness, you must also add tests demonstrating that any new code that you add (features, functions, etc.) has the expected behavior. Where possible, please ensure that code works correctly on edge cases (_e.g._, empty or disconnected dihypergraphs).

To reduce the likelihood of type-based errors, type-annotate all function inputs and, where appropriate, include type assertions and type-based tests.

### Efficiency

As soon as you have a correct implementation (with tests), make a PR. At that point, if necessary, we will work with you to improve performance.

Whenever possible, avoid introducing new dependencies, especially those that would significantly increase the compile time.

Profile your code and, where possible, write code to reuse memory use.

### Misc

If an algorithm/method was previously published (_e.g._, in a paper or conference presentation), include an appropriate citation.
At minimum, this should include a link or a digital object identifier (DOI).

Each PR should contain one logical enhancement to the codebase. Please avoid putting many unrelated changes in one PR.
